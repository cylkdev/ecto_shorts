# Writing Module and Function Documentation

This is the documentation standard for this project.

Follow it so a beginner can understand the public API, call it correctly on the first try, predict every user-observable behaviour, and verify that behaviour using examples.

## Definitions

Use `.agent/DEFINITIONS.md` as the source of truth for definitions used in this repository's standalone documentation system. If a reusable term is missing, add it there instead of defining it locally in this document.

## What counts as "documentation" in Elixir

Elixir documentation is Markdown attached to code.

* `@moduledoc` for modules.
* `@doc` for public functions, macros, and callbacks.
* `@typedoc` for public types.
* `@spec` to define the input and output shapes.
* `@doc false` to hide internal public functions from generated docs.
* `@doc group: "Category"` to organize functions into logical groups.
* `@moduledoc groups:` to define the ordering and descriptions of those groups.
* `@callback` for behaviour callbacks.

Readers will treat these docs as the source of truth, so they must be complete and accurate.

## Core rules

Write docs as boundary descriptions, not as implementation walkthroughs.
Describe only what a caller can observe at the boundary.
Include everything a caller can observe, even if it is not the return value.

Keep the docs self-contained.
A beginner must be able to succeed using only the doc on the module or function they are reading.

Use plain language.
Define non-obvious terms the first time you use them.

Make every sentence unambiguous.
Each sentence must have only one reasonable interpretation.

Keep vocabulary consistent across the repo.
Use the same term for the same concept everywhere.

Start with the summary.
The first line must tell the reader what this module or function does.

Organize every moduledoc with `##` section headers.
Break the content into named sections so a reader can scan and jump.

Teach progressively.
Start with the simplest case and add complexity section by section.
Weave code examples into the prose wherever they clarify a concept - do not save all examples for a single Examples section at the end.

Every module gets rich, tutorial-style documentation regardless of size.
There is no length constraint. A moduledoc can be 10 lines or 400 lines. The length must match the complexity and surface area of the module.

## Formatting conventions

Follow these rules in all `@moduledoc`, `@doc`, and `@typedoc` strings.

### Bullet lists

Use `*` as the list prefix, never `-`.

    * First item
    * Second item
      * Nested item

### Options

Use this exact format for every option key:

    * `:key` (default: `value`) - Observable effect on the caller.

When there is no default:

    * `:key` - Observable effect on the caller.

### Cross-references

Link to related modules and functions with backtick syntax:

    See `OtherModule` for details.
    See `OtherModule.func/2` for a lower-level API.
    See also `c:Ecto.Repo.all/2`, `c:Ecto.Repo.one/2`, and `c:Ecto.Repo.get/3`.

Use `c:` prefix for callback references.
Use `m:` prefix for linking to a module's moduledoc section, e.g. `m:Ecto.Query#module-query-prefix`.

Link to named sections within the same module:

    See the ["Shared options"](#module-shared-options) section.

### Callout boxes

Use admonition syntax for important warnings and notes:

    > #### Watch out {: .warning}
    >
    > Explanation of the danger or caveat.

    > #### Tip {: .info}
    >
    > Helpful hint.

For simple notes, use a blockquote with `NOTE:`:

    > NOTE: by using `Ecto.Schema`, an `:id` field is generated by default.

### Emphasis

Use `**bold**` for critical terms: `**wrong**`, `**all**`, `**full data**`.
Use backticks for all code references: module names, function names, option keys, atoms, types, and values.

## User-observable behaviour

"User-observable" means anything a caller can see happen at the boundary.
This includes return values, raised errors, logs, messages to other processes, database writes, files created, telemetry emitted, retries, timeouts, ordering, and concurrency effects.

If a caller could notice it, document it.

## How to write module docs

Every moduledoc is a self-contained guide organized with `##` section headers.
A reader who has never seen the module should be able to understand it, use it, and predict its behaviour from the moduledoc alone.

### Structure

Follow this structure. Use `##` headers for each section. Omit a section only if it genuinely does not apply - never omit observable behaviour.

**1. One-line summary**

The very first line. One plain sentence that starts with a verb and says what the module does.

    @moduledoc """
    Tracks capacity limits for in-memory tables using lock-free counters.

**2. Orientation**

A paragraph or two after the summary. Cover:

* What this module is for - the situations where a caller should reach for it.
* What this module is not for - the boundary that prevents common mistakes.
* How it fits into the surrounding system - name the modules it collaborates with and what role each plays.
* The public entry points - point a new reader to the functions they should start with and what each one does.

Include inline code examples whenever they help a reader understand the relationship between modules:

    `Bigtable.Tablet.Manager` creates a gate when it creates an active
    table. `Bigtable.Tablet.Worker` then uses it on every write:

        [Worker] --reserve--> [CapacityGate] --:full--> trigger rotation

**3. Conceptual sections** (`## Title`)

Break the module's behaviour into named sections. Each section explains one concept the reader needs.

Teach each concept progressively: start with the simplest case, then add complexity. Include inline code examples in every section - not just in the Examples section.

Examples of good section names:

* `## Key concepts`
* `## The write lifecycle`
* `## Validations and constraints`
* `## Topics & Callbacks`
* `## Configuration`
* `## Telemetry events`
* `## Instrumentation`

If a concept has sub-topics, use `###` sub-headers.

**4. Examples / First use** (`## Examples` or a purpose-led section title)

A copy-paste-able snippet showing the happy path from start to finish. This section must be runnable - a reader should be able to drop it into an IEx session and see it work.

    ## Run the first example

        {:ok, _pid} = Bigtable.start_link(name: :my_table, families: [:info])
        :ok = Bigtable.put(:my_table, "row:1", :info, "col", "value")
        {:ok, "value"} = Bigtable.get(:my_table, "row:1", :info, "col")

**5. Configuration** (`## Configuration`)

If the module accepts options at startup or has configurable behaviour, list them here using the `*` options format. Describe each option in terms of what the caller observes.

**6. Struct fields** (`## Fields` or `## The Struct`)

If the module defines a public struct, list each public field with its type and meaning.
Explicitly separate public fields from private/internal fields.

    ## The Ecto.Changeset struct

    The public fields are:

      * `valid?` - Stores if the changeset is valid
      * `data` - The changeset source data, for example, a struct
      * `params` - The parameters as given on changeset creation

    The following fields are private and must not be accessed directly.

      * `validations`
      * `constraints`

**7. Edge cases and warnings**

Use callout boxes for gotchas. Show anti-patterns explicitly with "The following approach is **wrong**:" followed by the correct way:

    The following approach is **wrong**:

        post
        |> Ecto.Changeset.change()
        |> Ecto.Changeset.put_assoc(:comments, [%Comment{body: "bad"}])
        |> Repo.update!()

    The reason is that `put_assoc/4` works with the **full data**, so
    the example above will **erase all previous comments**.

    Instead, work on the association directly:

        %Comment{body: "correct"}
        |> Ecto.Changeset.change()
        |> Ecto.Changeset.put_assoc(:post, post)
        |> Repo.insert!()

**8. Cross-references**

End the moduledoc with links to related modules, guides, and resources:

    See `Bigtable.Table` for the structured data API.
    See `Bigtable.Cluster` for direct cluster management.

### Function grouping in moduledocs

When a module has five or more public functions, group them by category:

    @moduledoc groups: [
      %{title: "Query API", description: "Functions that operate on queries."},
      %{title: "Schema API", description: "Functions that operate on schemas."},
      "Config API"
    ]

Then annotate each function with `@doc group: "Category"`.

## How to write function docs

### One-line summary

Start with a verb. One sentence that says what this function does.

### Contract in prose

State what each argument means in plain language.
If the function accepts more than one shape, list each accepted shape.

Describe the return value exactly.
Prefer concrete shapes like `{:ok, value}` and `{:error, reason}`.
If the function can raise, say what triggers the exception and what the caller will observe.

List side effects.
Mention logs, database writes, messages, telemetry, file IO, network calls, and any observable timing behaviour.

Only describe performance when it changes how a caller should use the function.

### Options

Use an `## Options` section when the function takes options. Use the `*` format:

    ## Options

      * `:timeout` (default: `5_000`) - How long the call waits before returning `{:error, :timeout}`.
      * `:mode` (default: `:safe`) - Selects validation rules that affect which inputs return `{:error, reason}`.

### Examples

Use an `## Examples` section with copy-paste-able examples.

Include at least:
* A happy-path example
* One realistic edge case or error case

Use `iex>` style for short interactive examples:

    ## Examples

        iex> MyApp.Payments.charge(order, [])
        {:ok, receipt}

Use plain code blocks (indented, no `iex>`) for longer multi-line examples. Add comments to explain what is happening:

    ## Examples

        # Fetch all post titles
        query = from p in Post, select: p.title
        MyRepo.all(query)

If output varies (time, randomness, network), say what varies and what stays stable.

### Cross-references

Add a "See also" line linking to related functions:

    See also `c:get!/3`, `c:one/2`, and `c:all_by/3`.

### Bang variants

For `func!/arity` that mirrors `func/arity`, use the "Similar to" pattern instead of duplicating the entire doc:

    @doc """
    Similar to `get/3` but raises `Ecto.NoResultsError` if no record was found.

    ## Options

    ...same options as `get/3`...
    """

### Scaling depth to complexity

Simple accessor functions (getters, predicates, delegations) get 2-5 lines.
Complex multi-clause functions with options, multiple input shapes, or subtle semantics get rich docs with multiple `##` sections, narrative prose, and many examples.

Match the depth to the function. If a caller could be surprised by the behaviour, the docs are not detailed enough.

## Multi-clause functions

Put `@doc` above the first clause.
If argument names inferred by Elixir would be confusing, add a function head to control names.

    def size(map_with_size)

    def size(%{size: size}) do
      size
    end

## How to write callback docs

Callback docs follow the same rules as function docs with these additions:

* State when the runtime invokes this callback and from which context (e.g., "called when the Repo supervisor is starting").
* Document every possible return value and what it causes the caller/runtime to do.
* Include an implementation example showing a typical callback body.

Example:

    @doc """
    Receives the socket params and authenticates the connection.

    ## Socket params and assigns

    Socket params are passed from the client and can be used to verify
    and authenticate a user. After verification, you can put default
    assigns into the socket:

        {:ok, assign(socket, :user_id, verified_user_id)}

    To deny connection, return `:error` or `{:error, term}`.

    See `Phoenix.Token` for examples of token verification on connect.
    """
    @callback connect(params :: map, Socket.t(), connect_info :: map) ::
                {:ok, Socket.t()} | {:error, term} | :error

## How to write type docs

Use `@typedoc` for any public type that is not immediately self-explanatory from its definition.

For types with multiple states or shapes, document each variant and when it occurs:

    @typedoc """
    Cache query metadata passed to `c:execute/5`.

    The cache can be in 3 states:

      * `{:nocache, prepared}` - the query cannot be cached. `prepared`
        is the value returned by `c:prepare/2`.

      * `{:cache, cache_function, prepared}` - the query can be cached.
        Call `cache_function` with your cache entry to store it.

      * `{:cached, update_function, reset_function, cached}` - the query
        has been cached. Call `update_function/1` to update the entry or
        `reset_function/1` to force re-caching.
    """
    @type query_cache :: {:nocache, prepared}
                         | {:cache, (cached -> :ok), prepared}
                         | {:cached, (cached -> :ok), (prepared -> :ok), cached}

Reference the type in related function docs so readers can find it.

## `@doc false` and internal functions

Use `@doc false` for public functions that are implementation details and should not appear in generated documentation. Common cases:

* `__using__/1`, `__before_compile__/1`, and other compiler callbacks
* Functions that are public only because they are called across module boundaries internally
* Delegation targets that callers should not use directly

Do not use `@doc false` to hide functions that callers might need. If a function is part of the public contract, document it.

## OTP modules

If a module starts or supervises processes, document startup and crash behaviour in caller terms.

Cover these in dedicated `##` sections:

* **How to start** - what arguments are required, what `start_link/1` returns, where it fits in a supervision tree.
* **Supervision tree context** - ASCII diagram or prose showing where this process sits relative to its parent and siblings.
* **Crash and restart behaviour** - what happens to in-flight work, what state survives, what the caller observes during recovery.
* **Messages** - if the module sends or expects specific messages (e.g., `{:DOWN, ...}`, `{:"ETS-TRANSFER", ...}`), document them and what the caller should do.

Use `## Examples` for a start-and-use snippet.

## Templates

Use these as starting points. Adapt the structure to fit the module. Delete sections that do not apply, but never omit observable behaviour.

Module template:

    defmodule MyApp.Example do
      @moduledoc """
      Does one clear thing in one sentence.

      Use this module when (describe the situation). Do not use this module
      when (describe the boundary). Most callers should use `MyApp.Facade`
      instead; reach for this module when you need (specific reason).

      This module is responsible for (describe caller-visible responsibilities).
      It is not responsible for (important non-goals).

      ## Key concepts

      A **widget** is (definition). Widgets are (how they relate to the system).

      Start with `new/1` when you need (one-line outcome):

          {:ok, widget} = MyApp.Example.new(%{name: "demo"})

      Call `run/2` to (one-line outcome):

          {:ok, result} = MyApp.Example.run(widget, timeout: 5_000)

      ## Configuration

      `new/1` accepts these options:

        * `:timeout` (default: `5_000`) - How long `run/2` waits before
          returning `{:error, :timeout}`.
        * `:mode` (default: `:safe`) - Selects validation rules.

      ## Error handling

      On success `run/2` returns `{:ok, result}`.
      On failure it returns `{:error, reason}` where `reason` is one of:

        * `:timeout` - the operation exceeded the configured timeout
        * `:invalid_input` - the widget struct was malformed

      It raises `ArgumentError` when `widget` is not a `%MyApp.Example{}` struct.

      > #### Watch out {: .warning}
      >
      > Calling `run/2` on a widget that has already been consumed will
      > return `{:error, :already_consumed}`. Create a new widget instead.

      ## Examples

          iex> {:ok, w} = MyApp.Example.new(%{name: "demo"})
          iex> MyApp.Example.run(w, timeout: 1_000)
          {:ok, %{status: :done}}

      See `MyApp.Facade` for the high-level API.
      See `MyApp.Example.Store` for persistence.
      """

      @moduledoc groups: [
        "Lifecycle",
        "Query"
      ]
    end

Function template:

    @doc """
    Does one thing in one sentence.

    `arg1` is (plain meaning and accepted shapes).
    `arg2` is (plain meaning and accepted shapes).

    Returns `{:ok, value}` on success. Returns `{:error, reason}` when
    (describe triggers). Raises `ArgumentError` when (describe trigger).

    It also (side effects).

    See also `other_func/2` and `related_func/1`.

    ## Options

      * `:timeout` (default: `5_000`) - How long to wait before returning
        `{:error, :timeout}`.

    ## Examples

        iex> MyApp.Example.run(arg1, arg2)
        {:ok, value}

        # With explicit timeout
        iex> MyApp.Example.run(arg1, arg2, timeout: 1_000)
        {:ok, value}

        # Error case
        iex> MyApp.Example.run(nil, arg2)
        {:error, :invalid_input}
    """
    @doc group: "Lifecycle"
    @spec run(arg1_type, arg2_type, Keyword.t()) :: {:ok, term} | {:error, atom}
    def run(arg1, arg2, opts \\ []) do
      ...
    end

## Done means "fully described"

Consider docs done only when a beginner can answer these from the doc they are reading:

* They can explain when to use it and when not to.
* They can provide valid inputs without guessing shapes or required keys.
* They can predict return values and error shapes.
* They can predict side effects.
* They can predict relevant ordering, concurrency, retries, and timeouts.
* They can verify behaviour using the examples.

Additionally, verify these structural requirements:

* Every moduledoc has `##` section headers.
* Every section contains at least one inline code example.
* Every option uses the `*` format: `* `:key` (default: `val`) - effect`.
* Every function has a "See also" or cross-reference to related functions.
* Complex public types have `@typedoc`.
* Internal public functions use `@doc false`.
* Modules with 5+ public functions use `@doc group:` and `@moduledoc groups:`.

If any user-observable behaviour is missing, the docs are not done.
